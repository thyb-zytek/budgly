# RL-01 — App Initialization, Onboarding & Caching Engine

* **Objective**: Manage user authentication, guide new users through the onboarding flow, and initialize application state using an offline-first caching policy across Supabase and Firestore.
* **Scope**: Authentication, Onboarding, Cache Management, and Initial Data Sync.

---

## 1. Authentication & Profile Logic

### 1.1 Authentication Methods
* **Google Sign-In**: Considered automatically verified upon successful OAuth authentication.
* **Email & Password**: Requires email verification. Users registering via email receive a validation email.

### 1.2 User Profile Creation
Upon registration (if the user does not exist), a profile entry is created in Supabase adhering to the `UserProfile` schema:
* **Fields**: `id`, `email`, `fullName`, `avatarUrl`, `color`, `themeMode`, `currency`, `amountDecimalPlaces`, `language`, `accounts`, `onboardingCompleted`, `createdAt`, `updatedAt`.

### 1.3 Application Preferences Loading
Upon any successful sign-in, user preferences stored in `UserProfile` are immediately applied to the local app state:
* `themeMode`
* `currency`
* `language`
* `amountDecimalPlaces`

## 2. Onboarding Workflow

The onboarding state is determined by the `UserProfile.onboardingCompleted` flag:
```text
                  ┌──────────────────────────────┐
                  │      User Authenticated      │
                  └──────────────┬───────────────┘
                                 │
                   [Is onboardingCompleted true?]
                                 │
                   ┌─────────────┴─────────────┐
                   │                           │
                ( NO )                      ( YES )
                   │                           │
                   ▼                           ▼
       Check SharedPreferences         Bypass Onboarding
     for saved `onboarding_step`      Redirect to Overview Page
                   │                           │
         ┌─────────┴─────────┐                 │
      (Found)           (Not Found)            │
         │                   │                 │
         ▼                   ▼                 │
   Resume at Step     Start at Step 1          │
  (with pre-loaded)  (with pre-loaded)         │
         │                   │                 │
         └─────────┬─────────┘                 │
                   │                           │
                   ▼                           ▼
        Execute Onboarding Steps ──────> Load App Data
```
### 2.1 Onboarding Steps Sequence
1. **Step 1 — Presentation Screen**: Introductory app overview screen.
2. **Step 2 — Account Creation**: Setup of the first financial `Account` in Supabase.
3. **Step 3 — Category Setup**: Creation of at least one (or multiple) `Category` records in Supabase.
4. **Step 4 — Revenue Setting (Optional)**: Input of the current period income, stored in Firestore under the `AccountBudget` collection (`id`, `accountId`, `year`, `month`, `revenue`, `updatedAt`).

### 2.2 Onboarding Step Persistence
* The current onboarding step index is stored in local storage (`SharedPreferences`).
* If the user quits and re-opens the app prior to completing onboarding:
  * If `onboarding_step` exists in `SharedPreferences`, the app resumes at that specific step with previously entered data pre-loaded.
  * If `onboarding_step` is missing, onboarding restarts at **Step 1** while maintaining any already-created backend records.
* Upon completion of Step 4, `UserProfile.onboardingCompleted` is updated to `true` on Supabase, and the app redirects to the **Overview Page**.

## 3. Data Loading & Offline-First Caching Engine

### 3.1 Data Scope & Stores
* **Supabase Data**: `UserProfile`, `Account` list, `Category` list.
* **Firestore Data**: 
  * `AccountBudget` for the current month/year (`year = current_year`, `month = current_month`).
  * `Expense` records for the current period (`debitDate` in current month/year).
  * Past non-debited `Expense` records (`isDebited = false` from prior periods).

### 3.2 Caching Strategy: Cache-First with Background Revalidation
The application uses a **Cache-First with Stale-While-Revalidate** policy without time-based expiration timers:

* **Non-Empty Cache**:
  1. Instantly load and render data from the local cache.
  2. Silently initiate a background network request to revalidate and fetch fresh data from the server (Supabase / Firestore).
  3. If server data differs from local cache, update the local cache and refresh the UI gracefully.
* **Empty Cache**:
  1. Block the screen or component with a primary loading state (Skeleton / Spinner).
  2. Initiate an immediate server fetch with a configurable timeout (`app_constants.networkTimeout`).
  3. **On Success**: Populate local cache and render the page.
  4. **On Failure / Timeout (Offline)**: If the network request fails or times out and no cached data exists, render an offline error state with a "Retry" prompt.

### 3.3 Offline Fallback & Background Retry
* If a network error or timeout occurs during revalidation (when cache is present), the app continues serving cached data seamlessly without blocking the user.
* Background workers monitor connection restoration and queue retries automatically.

### 3.4 Data Mutation Protocol (Optimistic UI)
* All mutations (Create, Update, Delete) write **immediately to the local cache** to reflect UI changes instantly.
* A background sync job is queued to persist changes to Supabase/Firestore.
